# Validation Benchmark

This benchmark compares three Kotlin validation approaches using the same logical validation rules and equivalent benchmark data:

| Library                | Mechanism                                               |
| ---------------------- | ------------------------------------------------------- |
| **Nok Validation**     | Compile-time code generation via Kotlin compiler plugin |
| **Jakarta Validation** | Runtime constraint validation                           |
| **Konform**            | Runtime DSL validation                                  |

The benchmark measures the cost of **validating an already-created DTO**. DTO construction, validation setup, and test-data generation are performed outside the measured benchmark methods.

## DTO Under Test

All three implementations validate the same logical rules:

* `name` must not be blank
* `name` length must be between 3 and 10 characters
* `name` must contain `"meow"`
* every `favoriteToys` element must contain `"42"`

### Nok Validation

```kotlin
@Validatable
data class CreateCatDto(
    val name: String = schema {
        isNotBlank()
        length(3, 10)
        contains("meow")
    },
    val favoriteToys: List<String> = schema {
        forEach {
            contains("42")
        }
    }
)
```

### Jakarta Validation

```kotlin
data class CreateCatDto(
    @field:NotBlank
    @field:Size(min = 3, max = 10)
    @field:Contains("meow")
    val name: String,

    val favoriteToys: List<@Contains("42") String>
)
```

A custom `@Contains` constraint and corresponding `ConstraintValidator` are used to express the same validation rules.

### Konform

```kotlin
data class CreateCatDto(
    val name: String,
    val favoriteToys: List<String>
)

object CreateCatDtoValidation {
    val validation = Validation {
        CreateCatDto::name {
            constrain { it.isNotBlank() }
            minLength(3)
            maxLength(10)
            constrain { it.contains("meow") }
        }

        CreateCatDto::favoriteToys onEach {
            constrain { it.contains("42") }
        }
    }
}
```

## Benchmark Data

Benchmark data is generated by `CatDtoBenchmarkData` for Jakarta Validation and Konform, and by the equivalent `CatDtoGenerator` for Nok.

The generators use the same pools of valid and invalid values.

### Valid values

Five valid names:

```text
meowMilo
meowLuna
meowNala
meowOscar
meowSimba
```

Five valid toys:

```text
ball42
mouse42
feather42
laser42
spring42
```

### Invalid values

Five invalid names:

```text
Milo
Luna
Oscar
cat
verylongcatname
```

Five invalid toys:

```text
ball
mouse
feather
laser
""
```

When randomized data is enabled:

* names are randomly selected from the corresponding pool;
* toys are randomly selected from the corresponding pool;
* `favoriteToys` contains between **1 and 5 elements**.

The invalid generator creates an invalid name and an invalid toy element by default.

When randomization is disabled, deterministic data is used with **3 toy elements**.

All test data is generated during `@Setup(Level.Trial)` and is therefore **not included in the measured validation time**.

## Methodology

The benchmark uses [JMH](https://github.com/openjdk/jmh) in `AverageTime` mode.

### JMH Configuration

* **Benchmark mode:** `AverageTime`
* **Output unit:** `ns/op`
* **Forks:** 3
* **Warmup:** 300 iterations × 20 ms
* **Measurement:** 200 iterations × 20 ms
* **Profiler:** GC (`-prof gc`)
* **State:** `Scope.Thread`

Each benchmark reuses pre-created DTO instances. This isolates validation performance from DTO allocation and test-data generation.

### Scenarios

| Scenario    | Description                            |
| ----------- | -------------------------------------- |
| **Valid**   | 100% valid DTOs                        |
| **Invalid** | 100% invalid DTOs                      |
| **Mixed**   | 4 valid → 1 invalid (20% failure rate) |
| **Rare**    | 99 valid → 1 invalid (1% failure rate) |

The `Mixed` and `Rare` scenarios cycle through pre-built arrays, keeping the failure rate deterministic during the benchmark.

### Relative Performance

The measured results correspond to the following speedups:

| Scenario | Nok vs Jakarta | Nok vs Konform |
| -------- | -------------: | -------------: |
| Valid    |     **~39.1×** |      **~4.5×** |
| Invalid  |     **~21.8×** |      **~5.9×** |
| Mixed    |     **~35.2×** |      **~4.7×** |
| Rare     |     **~44.6×** |      **~7.7×** |

On the valid path, Nok requires **11.8 ns/op** with approximately **0 B/op measured allocation**.

On the invalid path, Nok measures **235 B/op**, compared with **4,923 B/op** for Jakarta Validation — approximately **21× less measured allocation**.

These numbers describe this specific benchmark workload and should not be interpreted as universal application-level speedups.

## Why Nok Is Fast

Nok moves validation logic to compile time.

The compiler plugin processes the validation schema and generates the validation implementation directly into the DTO.

At runtime, the generated implementation is ordinary JVM code operating directly on the DTO rather than interpreting a validation schema.

Conceptually, the generated implementation looks like:

```java
public final List generated$validate() {
    ValidationResultList var1 = new ValidationResultList();

    // name: isNotBlank()
    if (StringsKt.isBlank(this.name)) {
        var1.add("name is blank!");
    }

    // name: length(3, 10)
    int len = this.name.length();
    if (3 <= len ? len > 10 : true) {
        var1.add("name length " + this.name + " dont falls in range 3..10");
    }

    // name: contains("meow")
    if (!StringsKt.contains$default(
            this.name, "meow", false, 2, null)) {
        var1.add("name " + this.name + " dont contains meow!");
    }

    // favoriteToys: forEach { contains("42") }
    for (Object toy : this.favoriteToys) {
        if (!StringsKt.contains$default(
                (String) toy, "42", false, 2, null)) {
            var1.add(
                "favoriteToys " + toy + " dont contains 42!");
        }
    }

    return var1.list();
}
```

The code above is a simplified decompiled representation. Exact bytecode and generated implementation details depend on the Kotlin compiler version.

## Running the Benchmark

Build the JMH executable:

```bash
./gradlew :benchmarks:jmhJar
```

Run the benchmark with the GC profiler:

```bash
java -jar benchmarks/build/libs/benchmarks-1.0.0-jmh.jar \
    -prof gc \
    -rf text \
    -rff results.txt
```

To reproduce the results as closely as possible, use the same JVM, Kotlin version, library versions, and hardware configuration described above.


The complete benchmark implementation is available in this directory so the results can be independently inspected and reproduced.
